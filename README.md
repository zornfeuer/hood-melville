# hood-melville

Persistent real-time queue of Hood and Melville in C, Rust and Zig: worst-case O(1)
`push`, `pop` and `front`, every operation returns a new version.

Исследование и три реализации (C, Rust, Zig) функциональной (персистентной) очереди
реального времени на шести стеках по статье
[R. Hood, R. Melville. Real-time queue operations in pure LISP. *Information
Processing Letters*, 1981, 13(2), 50–54](https://doi.org/10.1016/0020-0190(81)90030-2).

Цель — максимально быстрые и корректные реализации одного алгоритма с
одинаковой семантикой и честное измерение того, какая из них быстрее.

## Что внутри

| путь | содержимое |
|---|---|
| `c/` | библиотека на C17: шаблон `include/fqueue_template.h` для любого типа элемента, экземпляры для `int` — `fqueue` и потокобезопасный `fqueue_sync` (`include/fqueue.h`, `src/fqueue.c`), тесты на Catch2, нагрузка для бенчмарков |
| `rust/` | крейт `hood-melville`: `Queue<T>` и потокобезопасная `SyncQueue<T>` (общий код, параметр счётчика `refcount::{Local, Atomic}`); `unsafe` только в `src/node.rs` (свой счётчик ссылок в узле), проверяется Miri |
| `zig/` | третья реализация на Zig 0.16 (идиоматичная, ещё не оптимизированная): `Queue(T)` и потокобезопасная `SyncQueue(T)` с явным аллокатором и ошибками через error union, тесты с проверкой утечек и отказа каждой аллокации, та же нагрузка |
| `bench/compare.py` | сравнение бинарников: чередование запусков, режимы аллокатора, несколько раскладок кода, бутстреп-интервалы |
| `docs/proof.md` | доказательство корректности и worst-case O(1) при одном шаге ротации на операцию |
| `docs/benchmarks.md` | методика измерений, журнал оптимизаций (что принято и что отклонено), результаты |
| `docs/c-implementation-notes.md` | заметки об исходной C-реализации (исторический документ) |

## Гарантии

- `push`/`pop` строят новую версию, не изменяя аргумент; версии разделяют узлы.
  Если старая версия больше не нужна, её можно изменить на месте
  (`push_mut`/`pop_mut` в Rust, `fqueue_push_in_place`/`fqueue_pop_in_place`
  в C): без копирования версии и освобождения старой, другие версии не
  затрагиваются.
- В каждой библиотеке два варианта с одинаковым API: однопоточный (`Queue`,
  `fqueue`, `Queue(T)`) и потокобезопасный на атомарных счётчиках ссылок
  (`SyncQueue`, `fqueue_sync`, `SyncQueue(T)`): версию могут читать и
  порождать из неё новые версии сразу несколько потоков, узлы разделяются
  между потоками. Проверки: Miri (Rust, с поиском гонок данных), ThreadSanitizer
  (C), многопоточные модельные тесты во всех трёх языках.
- Worst-case O(1) на построение версии и доступ: не больше 3 новых узлов на
  `push` и 2 на `pop`; для обобщённого `T` — плюс не более двух `T::clone`.
- Уничтожение версии **не** O(1) в худшем случае: освобождается всё, чем она
  владела монопольно. Амортизированно это O(1) на операцию.
- Доказательство — `docs/proof.md`; проверки — полный перебор коротких историй,
  property-based тесты против эталонной модели (включая ветвящиеся истории),
  Miri для Rust, ASan/UBSan для C.

## Использование

C — версии хранятся по значению в памяти вызывающего, как `Queue` в Rust:

```c
#include "fqueue.h"

fqueue a, b;
fqueue_init(&a);
fqueue_status s = fqueue_push(&b, &a, 42); // a не изменилась
if (s != FQUEUE_OK) {                      // FQUEUE_NOMEM / FQUEUE_OVERFLOW:
  fprintf(stderr, "%s\n", fqueue_strerror(s)); // b не инициализирована
  ...
}
int x;
fqueue_front(&b, &x);           // true, x == 42
fqueue_destroy(&a);
fqueue_destroy(&b);
```

Библиотека не завершает процесс: нехватка памяти и переполнение длины или
счётчика ссылок возвращаются как `fqueue_status`, аргумент при этом не
меняется. В Rust те же ситуации, как принято в языке, — паника (`push` в
очередь из `u32::MAX` элементов) или `abort` (переполнение счётчика, OOM).

Очередь для своего типа элемента — экземпляр шаблона (элементы копируются
присваиванием, как в klib):

```c
// strq.h                          // strq.c
#define FQUEUE_NAME strq           #include "strq.h"
#define FQUEUE_T    const char *   #define FQUEUE_NAME strq
#include "fqueue_template.h"       #define FQUEUE_T    const char *
                                   #define FQUEUE_IMPLEMENTATION
                                   #include "fqueue_template.h"
```

Получаются тип `strq` и функции `strq_init`, `strq_push`, `strq_pop`,
`strq_push_in_place`, `strq_pop_in_place`, `strq_front`, `strq_clone`,
`strq_destroy`, итератор `strq_iter_*`.

Изменение на месте — то же, что новая версия с удалением старой, но дешевле;
при ошибке очередь не меняется:

```c
fqueue q;
fqueue_init(&q);
fqueue_status s = fqueue_push_in_place(&q, 1);
int x;
s = fqueue_pop_in_place(&q, &x);   // FQUEUE_OK, x == 1; FQUEUE_EMPTY для пустой
```

Rust:

```rust
use hood_melville::Queue;

let q1 = Queue::new().push(1).push(2);
let q2 = q1.pop().unwrap();
assert_eq!(q1.front(), Some(&1)); // старая версия не изменилась
assert_eq!(q2.front(), Some(&2));

let mut q = q2.clone();
q.push_mut(3);                    // на месте; q2 не изменилась
assert_eq!(q.pop_mut(), Some(2));
```

Потокобезопасный вариант — `SyncQueue<T>` (`Send + Sync` при `T: Send + Sync`):

```rust
use hood_melville::SyncQueue;

let base: SyncQueue<i32> = (1..=3).collect();
std::thread::scope(|s| {
    for i in 0..4 {
        let base = &base;
        s.spawn(move || assert_eq!(base.push(i).len(), 4)); // base общий
    }
});
```

В C — `fqueue_sync` с тем же API (`fqueue_sync_push`, …), в Zig —
`SyncQueue(T)`.

## Результаты (Apple M5, 4 раскладки кода × 8 раундов)

Такты, млн — медиана быстрого режима; C собран с `-O3 -flto`, Rust — fat LTO,
Zig — `ReleaseFast`, все под `native`; версии хранятся по значению. Раскладки
версии лучшие для каждого языка: Rust — 64 байта (одна строка кэша), C — 80
(на 64 C проигрывал себе, см. журнал), Zig — 72 (ещё не оптимизирован). У Zig
нет опций выравнивания кода, его четыре «раскладки» — одна сборка.

**Персистентные операции, одинаковые истории** (структура данных как таковая):

| сценарий | C | Rust | Zig | Rust / C (95% CI) | Zig / C (95% CI) |
|---|---:|---:|---:|---|---|
| fill 10^6 | 179.8 | 185.8 | 208.2 | 1.033 (1.014–1.063) | 1.158 (1.138–1.173) |
| mixed 10^6 | 335.2 | 362.2 | 407.7 | 1.081 (1.054–1.129) | 1.216 (1.189–1.238) |
| persistent 10^6 | 460.9 | 471.5 | 590.3 | 1.023 (1.006–1.054) | 1.281 (1.264–1.297) |
| branching 10^6 | 201.7 | 199.7 | 228.0 | 0.990 (0.964–1.024) | 1.130 (1.092–1.157) |
| fill 10^7 | 1764.5 | 1890.0 | 2021.5 | 1.071 (1.035–1.090) | 1.146 (1.123–1.169) |
| mixed 10^7 | 3482.8 | 3771.3 | 4629.6 | 1.083 (1.032–1.184) | 1.329 (1.287–1.363) |

**Операции на месте** (`push_mut`/`pop_mut`, `*_in_place`, `pushInPlace`/`popInPlace`):

| сценарий | C | Rust | Zig | Rust / C (95% CI) | Zig / C (95% CI) |
|---|---:|---:|---:|---|---|
| fill_mut 10^6 | 162.1 | 152.0 | 191.5 | 0.937 (0.913–0.953) | 1.181 (1.152–1.212) |
| mixed_mut 10^6 | 340.3 | 298.3 | 386.6 | 0.877 (0.831–0.925) | 1.136 (1.097–1.209) |
| fill_mut 10^7 | 1605.5 | 1562.1 | 2339.9 | 0.973 (0.903–1.017) | 1.457 (1.384–1.545) |
| mixed_mut 10^7 | 3362.1 | 2871.5 | 6735.9 | 0.854 (0.830–0.898) | 2.003 (1.922–2.057) |

**Идиоматичная программа**: одна задача, те же живые версии, каждый язык в
лучшей из своих форм (C — два буфера или `*_in_place`, Rust — `push`/`pop` или
`push_mut`/`pop_mut`, Zig — `push`/`pop` или `pushInPlace`/`popInPlace`); в
`persistent`/`branching` все версии живы, форма одна. Отношения медиан, без
интервалов (строки из разных сценариев):

| задача | C | Rust | Zig | Rust / C | Zig / C |
|---|---:|---:|---:|---:|---:|
| fill 10^6 | 162.1 (на месте) | 152.0 (на месте) | 191.5 (на месте) | 0.94 | 1.18 |
| mixed 10^6 | 335.2 (два буфера) | 298.3 (на месте) | 386.6 (на месте) | 0.89 | 1.15 |
| persistent 10^6 | 460.9 | 471.5 | 590.3 | 1.02 | 1.28 |
| branching 10^6 | 201.7 | 199.7 | 228.0 | 0.99 | 1.13 |
| fill 10^7 | 1605.5 (на месте) | 1562.1 (на месте) | 2021.5 (персист.) | 0.97 | 1.26 |
| mixed 10^7 | 3362.1 (на месте) | 2871.5 (на месте) | 4629.6 (персист.) | 0.85 | 1.38 |

Выводы:

- На персистентных операциях C быстрее Rust на 2–8%, в `branching` — вровень.
  Остаток в основном из-за переносов версии: C пишет результат прямо в слот,
  у Rust гарантированного размещения результата нет (журнал, `docs/benchmarks.md`).
- В идиоматичной программе Rust быстрее C на 3–15% везде, где можно менять
  версию на месте, и вровень там, где все версии живы. Оговорка: в C операции
  на месте платят за гарантию «при ошибке без изменений», в Rust ошибки —
  паника/`abort`.
- Zig пока медленнее C на 13–33% (на месте при 10^7 — до 2×, при
  инструкциях +12%: дело в памяти, а не в коде); его оптимизация впереди.
- Распределения, режимы аллокатора, влияние раскладки кода и все отклонённые
  эксперименты — `docs/benchmarks.md`.

### Параллельная нагрузка (`just bench-par`, issue #6)

Потокобезопасные варианты, 10 потоков (4 P- + 6 E-ядер), 256 независимых
задач; доля операций, родитель которых — одна из общих версий, меняется от 0
до 100%. Млн операций/с при P=10 и ускорение относительно одного потока:

| доля общих | C | Rust | Zig |
|---|---|---|---|
| 0% | 209 (4.8×) | 214 (5.9×) | 190 (6.0×) |
| 1% | 117 (3.1×) | 121 (2.9×) | 105 (3.4×) |
| 10% | 71 (2.1×) | 71 (2.1×) | 66 (2.2×) |
| 50% | 32 (1.0×) | 32 (1.1×) | 34 (1.3×) |
| 100% | 20 (0.6×) | 20 (0.6×) | 21 (0.8×) |

Масштабирование ломается уже на 1% общих операций, при 50% параллельность
ничего не даёт, при 100% потоки только мешают друг другу. Счётчик ссылок
лежит в узле, и каждая операция над общей версией — атомарные RMW по горячим
строкам кэша; это цена персистентности на счётчиках ссылок, а не языка: от 5%
три реализации совпадают. Сценарий «писатель и читатели снимков», режимы
`pool` (rayon / OpenMP / `std.Io.Group`) и `threads` и все таблицы —
`docs/benchmarks.md`.

## Установка C-библиотеки

```
cmake -S c -B build/c -DCMAKE_BUILD_TYPE=Release [-DBUILD_SHARED_LIBS=ON]
cmake --build build/c
cmake --install build/c --prefix <prefix>
```

Ставятся `libfqueue` (очередь для `int`), заголовки `fqueue.h`,
`fqueue_common.h`, `fqueue_template.h` и пакет CMake:

```cmake
find_package(hood_melville 0.1 REQUIRED)
target_link_libraries(app PRIVATE hood_melville::fqueue)
```

Подключать можно и через `add_subdirectory`/`FetchContent` — тесты и нагрузка
тогда не собираются (`HOOD_MELVILLE_BUILD_TESTS`, `HOOD_MELVILLE_BUILD_BENCH`).
Разделяемая библиотека экспортирует только публичные функции. Пример —
`c/examples/consumer` (`just c-install-check`).

## Запуск

Нужны `cmake`, C/C++-компилятор, Rust (stable; nightly с `miri` — для
`rust-miri`), [`just`](https://github.com/casey/just), Python 3.

```
just test                    # C- и Rust-тесты
just c-asan                  # C-тесты под ASan/UBSan
just c-tsan                  # многопоточные C-тесты под ThreadSanitizer
just c-leaks                 # C-тесты под leaks (macOS)
just c-install-check         # установка C-библиотеки и пример через find_package
just rust-lint               # rustfmt + clippy::pedantic
just rust-miri               # Rust-тесты под Miri
just zig-test                # Zig-тесты (zig build test)
just zig-lint                # zig fmt --check
just bench-compare-layouts   # сравнение C и Rust (несколько минут)
just bench-compare-mut       # то же для операций на месте
just bench-compare-sync      # цена потокобезопасных вариантов в одном потоке
just bench-par               # параллельная нагрузка: доля общих версий, снимки (C pool — libomp)
```
