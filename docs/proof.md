# Достаточность одного шага ротации на операцию

Утверждение: в реализациях `c/include/fqueue_template.h` и `rust/src/{queue,rotation}.rs`
выполнение **одного** шага ротации на каждую операцию `push`/`pop` (вместо двух)
сохраняет корректность (FIFO, доступность `front`), персистентность и
worst-case O(1) операций. Ниже — модель, инвариант и доказательство его
сохранения; затем отдельно — стоимость и ограничения.

Обозначение: `s ≥ 1` — число шагов ротации на операцию. Доказательство ведётся
для произвольного `s ≥ 1`; случай `s = 2` — текущий код, `s = 1` — предлагаемый.

## 1. Модель

### 1.1. Списки

Стек — неизменяемый односвязный список. Для списка `X` пишем `X = [x_1, …, x_k]`,
`x_1` — вершина; `|X| = k`; `rev(X)` — обращение; `·` — конкатенация.
`drop(c, X)` — список без первых `c` элементов.

### 1.2. Состояние версии

Версия очереди — кортеж `Q = (n, f, r, F, R, ρ)`:

- `F` — живой фронт (вершина — самый старый элемент очереди), `f` — его длина
  (`front_len`);
- `R` — тыл (вершина — самый новый элемент), `r = |R|` (`rear_len`);
- `n` — число элементов (`len`/`size`);
- `ρ` — состояние ротации, одно из:
  - `Idle`;
  - `Rev(ok, F', RF, R', A)` — фаза разворота (`Reversing`, `HM_REVERSING`);
  - `App(ok, RF, A)` — фаза переноса (`Appending`, `HM_APPENDING`).

### 1.3. Переходы ротации

**Старт** (только из `Idle`, когда `r = f + 1`): пусть `m = f`, `F₀ = F`,
`R₀ = R`. Устанавливаются `ρ := Rev(m, F₀, [], R₀, [])`, `R := []`, `r := 0`.

**Шаг** `σ` (один вызов `rotate_step` / `step_mut`):

- `Rev(ok, F', RF, R', A)`: снять вершину `y` с `R'` и положить на `A`; если `F'`
  не пуст — снять вершину `x` с `F'` и положить на `RF`. Если после этого `R'`
  пуст — переход в `App(ok, RF, A)` (при `ok = 0` — сразу завершение, см. ниже).
- `App(ok, RF, A)`: снять вершину `x` с `RF`, положить на `A`, `ok := ok − 1`;
  при `ok = 0` — завершение.
- `Idle`: ничего.

**Инвалидация** `ι` (в `pop` при идущей ротации): `ok := ok − 1`; в фазе `App`
при `ok = 0` — завершение.

**Завершение**: `F := A`, `f := n − r`, `ρ := Idle`; остаток `RF` отбрасывается.

### 1.4. Операции

`push(Q, x)`: `R := x · R`, `r += 1`, `n += 1`; если `ρ = Idle` и `r > f` —
старт; затем `s` шагов.

`pop(Q)` (только при `n > 0`): `F := drop(1, F)`, `f −= 1`, `n −= 1`; если
`ρ = Idle` и `r > f` — старт, иначе если `ρ ≠ Idle` — инвалидация; затем `s`
шагов.

`front(Q)` — вершина `F`.

**Соответствие коду.** В Rust шаг — ровно `σ` (`Rotation::step_mut`), завершение
внутри шага или инвалидации возвращает новый фронт (`install_front`). В C
`rotate_step` на шаге, исчерпывающем `R'`, сразу продолжает в ветку `App` и в том
же вызове выполняет проверку завершения и, возможно, ещё один шаг `App`; то есть
один вызов `rotate_step` выполняет **не меньше** работы, чем `σ`. Ниже
используется только нижняя оценка числа выполненных шагов, поэтому
доказательство покрывает обе реализации. Насыщающий декремент `ok` в C-версии
`fqueue_pop` по лемме 2 никогда не срабатывает.

## 2. Инвариант

Пусть `c` — число шагов `σ`, выполненных с момента старта текущей ротации,
`p` — число `pop`, выполненных после операции старта, `u` — число `push` после
операции старта. Заметим, что `R` обнуляется на старте, поэтому **`u = r`**.

Обозначим `F₀ = [a_1, …, a_m]`, `R₀ = [y_1, …, y_{m+1}]` (так что
`rev(R₀) = [y_{m+1}, …, y_1]` — тыл в порядке поступления).

**Инвариант `I(Q)`** (выполняется на границе операций):

- **(I-Idle)** `ρ = Idle`, `|F| = f`, `|R| = r`, `n = f + r`, **`r ≤ f`**,
  содержимое `⟦Q⟧ = F · rev(R)`.
- **(I-Run)** `ρ ≠ Idle`, и существуют `m ≥ 1`, `F₀`, `R₀` (как выше) и числа
  `c, p`, такие что:
  1. `F = [a_{p+1}, …, a_m]`, `f = m − p`, `|R| = r`;
  2. **`1 ≤ f`**, т. е. `p ≤ m − 1`;
  3. если `ρ = Rev(ok, F', RF, R', A)`: `c ≤ m`, `F' = drop(c, F₀)`,
     `RF = [a_c, …, a_1]`, `R' = drop(c, R₀)`, `A = [y_c, …, y_1]`, `ok = m − p`;
  4. если `ρ = App(ok, RF, A)`: `c = m + 1 + d` для некоторого `d ≥ 0`,
     `RF = [a_{m−d}, …, a_1]`, `A = [a_{m−d+1}, …, a_m] · rev(R₀)`,
     `ok = m − p − d ≥ 1`;
  5. **(T)** `c ≥ s · (1 + p + r)` — шаги, выполненные с момента старта, не
     меньше `s` на каждую операцию с момента старта, включая её саму;
  6. `n = f + (m + 1) + r` и `⟦Q⟧ = F · rev(R₀) · rev(R)`.

Пустая очередь `(0, 0, 0, [], [], Idle)` удовлетворяет (I-Idle).

## 3. Леммы

**Лемма 1 (старт).** Если `Q` удовлетворяет (I-Idle), то после примитивной
части операции (до старта и шагов) `r ≤ f + 1`; старт происходит тогда и только
тогда, когда `r = f + 1`.

*Доказательство.* До операции `r ≤ f`. `push` увеличивает `r` на 1, `pop`
уменьшает `f` на 1 (и `pop` допустим: `n = f + r > 0` и `r ≤ f` дают `f ≥ 1`,
т. е. `F ≠ []`). В обоих случаях `r ≤ f + 1`, а условие старта `r > f`
равносильно `r = f + 1`. ∎

Отсюда при старте `|R₀| = m + 1 = |F₀| + 1`, и фаза `Rev` длится ровно `m + 1`
шагов: на шаге `c ≤ m` из `F'` снимается элемент, на шаге `m + 1` `F'` уже пуст,
а `R'` исчерпывается — переход в `App`. Это обосновывает формулы п. 3 инварианта
и утверждение `debug_assert!(front.is_empty())` в коде.

**Лемма 2 (инвалидация допустима).** Если `Q` удовлетворяет (I-Run) и
выполняется `pop`, то перед декрементом `ok ≥ 1`, а удаляемый элемент берётся из
непустого `F`.

*Доказательство.* `F ≠ []` по п. 2. В `Rev`: `ok = m − p ≥ 1` по п. 2. В `App`:
`ok ≥ 1` по п. 4. ∎

**Оставшаяся работа.** Для состояния ротации определим

```
W(Idle)                   = 0
W(Rev(ok, F', RF, R', A)) = |R'| + ok
W(App(ok, RF, A))         = ok
```

Смысл: `W` — число шагов `σ` до завершения, если больше не будет `pop`
(`|R'|` шагов до конца `Rev`, затем `ok` шагов `App`).

**Лемма 3 (потенциал).**
1. Ротация идёт тогда и только тогда, когда `W ≥ 1`.
2. Каждый шаг `σ` при идущей ротации уменьшает `W` ровно на 1.
3. Каждая инвалидация уменьшает `W` ровно на 1.
4. Сразу после старта `W = 2m + 1`. Следовательно, при идущей ротации
   **`W = 2m + 1 − c − p`**, и на границе операций с идущей ротацией
   **`c ≤ 2m − p`**.

*Доказательство.*
1. В `Rev` `|R'| ≥ 1`: переход в `App` происходит в тот же шаг, в который
   `R'` становится пустым. В `App` `ok ≥ 1`: при `ok = 0` происходит
   завершение. В `Idle` `W = 0`.
2. Шаг в `Rev` уменьшает `|R'|` на 1 и не меняет `ok`. Если `R'` становится
   пустым, состояние становится `App(ok, …)` с тем же `W = ok`, а при `ok = 0`
   — `Idle` с `W = 0 = ok`; в обоих случаях значение `W` то же, что сразу после
   уменьшения `|R'|`. Шаг в `App` уменьшает `ok` на 1; при `ok = 0` —
   завершение, `W = 0`.
3. Инвалидация уменьшает `ok` на 1 и не меняет `|R'|`. В `App` при `ok = 0` —
   завершение, `W = 0`. В `Rev` ротация продолжается (`|R'| ≥ 1`), но `W`
   уменьшилось на 1.
4. При старте `|R'| = |R₀| = m + 1` (лемма 1), `ok = m`. За `c` шагов и `p`
   инвалидаций (инвалидация — ровно каждый `pop` после операции старта) `W`
   уменьшилось на `c + p`. По п. 1 при идущей ротации
   `W = 2m + 1 − c − p ≥ 1`. ∎

Связь с п. 3–4 инварианта: в `Rev` `|R'| = m + 1 − c`, `ok = m − p`; в `App`
`ok = m − p − d`, `c = m + 1 + d`; в обоих случаях `W = 2m + 1 − c − p`.

**Следствие 3 (запас до завершения).** Для версии в (I-Run) из (T) и леммы 3
`s(1 + p + r) ≤ c ≤ 2m − p`, откуда при `s ≥ 1`

```
r ≤ 2m − 2p − 1.
```

## 4. Сохранение инварианта

**Теорема 1.** Если `Q` удовлетворяет `I`, то `push(Q, x)` и (при `n > 0`)
`pop(Q)` удовлетворяют `I`, причём `⟦push(Q, x)⟧ = ⟦Q⟧ · [x]` и
`⟦pop(Q)⟧ = drop(1, ⟦Q⟧)`.

*Доказательство.* Разбор случаев по состоянию в начале операции.

**(а) `Q` в Idle, старта нет.** По лемме 1 `r ≤ f` сохраняется; шаги на `Idle`
ничего не делают; содержимое меняется ровно как у очереди:
`F · rev(x · R) = F · rev(R) · [x]`, `drop(1, F) · rev(R) = drop(1, F · rev(R))`
(так как `F ≠ []`). (I-Idle) выполняется.

**(б) `Q` в Idle, старт.** По лемме 1 `m = f`, `|R₀| = m + 1`, `p = 0`, `r = 0`,
`W = 2m + 1`. Содержимое `F · rev(R₀)` — то же, что до старта. Далее выполняются
`s` шагов, но не больше `W`: по лемме 3 после `k` шагов `W = 2m + 1 − k`, и
ротация завершается ровно на шаге `2m + 1`. Возможны три исхода (для любого
`s ≥ 1`):
- **`s ≤ m`**: фаза `Rev` с `c = s ≤ m`; `F = F₀`, `f = m ≥ 1`, (T): `c = s ≥ s·1`.
  (I-Run) выполняется.
- **`m + 1 ≤ s ≤ 2m`**: `Rev` завершён на шаге `m + 1`, дальше `d = s − m − 1`
  шагов `App`; `ok = m − d = 2m + 1 − s ≥ 1`, `F = F₀`, `f = m ≥ 1`, (T) верно.
  (I-Run) выполняется.
- **`s ≥ 2m + 1`** (в частности, `m = 0` при любом `s`): ротация завершена в этой
  же операции без `pop` (`p = 0`), новый фронт `A = F₀ · rev(R₀)` (п. 4 при
  `d = m`), `f' = n`, `r = 0 ≤ f'`. Оставшиеся шаги применяются к `Idle` и
  ничего не меняют. (I-Idle) выполняется.

**(в) `Q` в Run, операция — `push`.** `r := r + 1`; затем `s` шагов (пока ротация
не завершилась). Содержимое: `F · rev(R₀) · rev(x · R) = ⟦Q⟧ · [x]`.
- Если ротация не завершилась: `c' = c + s ≥ s(1 + p + r) + s = s(1 + p + (r + 1))`
  — (T) сохраняется. Пункты 3/4 сохраняются по определению `σ`, в том числе
  если внутри операции произошёл переход `Rev → App` (при `c' ≥ m + 1`; по
  лемме 1 к этому шагу `F'` уже пуст и `RF = [a_m … a_1]`).
  П. 2: в `Rev` `c' ≤ m` и (T) дают `1 + p + r ≤ c'/s ≤ m`, откуда `p ≤ m − 1`; в
  `App` `ok = m − p − d ≥ 1` (ротация не завершена) даёт `p ≤ m − 1 − d ≤ m − 1`.
- Если завершилась — см. (д).

**(г) `Q` в Run, операция — `pop`.** По лемме 2 `pop` берёт `a_{p+1}` из `F`, и
инвалидация допустима; `p := p + 1`, `ok := ok − 1`. Содержимое:
`drop(1, F) · rev(R₀) · rev(R) = drop(1, ⟦Q⟧)`. Далее `s` шагов.
- Если ротация не завершилась (ни на инвалидации, ни на шагах):
  `c' = c + s ≥ s(1 + p + r) + s = s(1 + (p + 1) + r)` — (T) сохраняется; п. 2 —
  как в (в) с новым `p`: в `Rev` `1 + p' + r ≤ m`, в `App` `ok' ≥ 1`.
- Если завершилась — см. (д).

**(д) Завершение внутри операции.** Завершение возможно в трёх точках операции;
во всех трёх `ok = 0`. Обозначим через `p` число `pop` с учётом текущей
операции, через `F` — живой фронт после примитивной части операции
(`F = [a_{p+1}, …, a_m]`).

1. **На шаге `App`** (`ok` становится 0 после переноса): по п. 4
   `ok = m − p − d = 0` ⇒ `d = m − p` ⇒
   `A = [a_{p+1}, …, a_m] · rev(R₀) = F · rev(R₀)`.
2. **На шаге, завершающем `Rev`**, при `ok = 0`: `ok = m − p = 0` ⇒ `p = m`,
   `F = []`, `A = rev(R₀) = F · rev(R₀)`. Это возможно только в `pop`, который
   снял последний элемент живого фронта; по п. 2 инварианта до этой операции
   `p₀ ≤ m − 1`, так что `p = m` достигается ровно здесь.
3. **На инвалидации в `App`, до шагов операции** (`pop` при `ok = 1`): после
   `p := p + 1` имеем `ok = m − p − d = 0` с тем же `d` (шагов ещё не было), ⇒
   `d = m − p` ⇒ `A = [a_{p+1}, …, a_m] · rev(R₀) = F · rev(R₀)`. Все `s` шагов
   операции затем применяются к `Idle` и ничего не меняют. Инвалидация в `Rev`
   завершить ротацию не может: по лемме 3 там `W ≥ |R'| ≥ 1`.

   *В C* инвалидация только уменьшает `ok` (до 0), а завершение выполняет
   следующий вызов `rotate_step` той же операции. Он есть, потому что `s ≥ 1`.
   Проверка `ok == 0` в ветке `App` стоит до переноса, поэтому завершение
   происходит без шага: `A` то же, результат тот же.

Во всех случаях новый фронт `A = F · rev(R₀)`, поэтому
`⟦Q'⟧ = A · rev(R) = F · rev(R₀) · rev(R)` — содержимое сохранено;
`f' = n − r = |A| = (m − p) + (m + 1)`, `|R| = r`. Остаётся показать `r ≤ f'`.

Если завершение случилось в самой операции старта — это исход `s ≥ 2m + 1` в
(б), там `r = 0`. Иначе ротация шла на конце предыдущей операции со значениями
`p₀, r₀`, и по следствию 3 `r₀ ≤ 2m − 2p₀ − 1`. Текущая операция увеличивает на 1
либо `r`, либо `p`:
- `push`: `r = r₀ + 1 ≤ 2m − 2p₀`, `p = p₀`, `f' = 2m + 1 − p₀ > r`;
- `pop`: `r = r₀ ≤ 2m − 2p₀ − 1`, `p = p₀ + 1`, `f' = 2m − p₀ > r`.

Значит, `r ≤ f'` (даже `r < f'`), и (I-Idle) выполняется. После завершения
оставшиеся шаги операции применяются к `Idle` и ничего не меняют. Старт новой
ротации в этой же операции не проверяется, и он не нужен, так как `r ≤ f'`. ∎

**Следствие 1 (доступность `front`/`pop`).** Для любой версии, удовлетворяющей
`I`: `n > 0 ⇒ F ≠ []`. В (I-Idle) из `r ≤ f` и `n = f + r > 0`; в (I-Run) — п. 2.
Следовательно, `front` возвращает голову `⟦Q⟧` (голова `F` = голова `⟦Q⟧`, так
как `⟦Q⟧` начинается с `F`), а `pop` никогда не обращается к пустому фронту.

**Следствие 2 (FIFO).** По теореме 1 абстрактное содержимое любой версии,
полученной цепочкой операций из пустой очереди, равно результату тех же
операций над идеальной очередью-последовательностью.

## 5. Персистентность и ветвление

Каждая операция получает версию-родителя и создаёт новую: копирует его
структуру (O(1): поля и инкременты счётчиков ссылок) и изменяет **только копию**.
Узлы списков после создания не изменяются, кроме поля счётчика ссылок, которое
не входит в абстрактное содержимое. В Rust узел разбирается «по месту»
(`into_parts`) только при счётчике 1, то есть когда на него не ссылается ни одна
другая версия — множество узлов, достижимых из остальных версий, не меняется.

Инвариант `I` — свойство **одной** версии: в него входят только её поля и
списки (`m`, `p`, `c` восстанавливаются из `ok`, длин `A`, `RF`, `F`). Каждая
версия создаётся одной операцией из одного родителя, поэтому индукция по
графу версий (любой формы, в том числе с ветвлением) доказывает `I` для всех
версий, а значит, следствия 1–2 для каждой из них. Родитель при этом не
изменяется — это и есть персистентность. Применение операции к давно созданной
версии ничем не отличается от применения к свежей.

## 6. Стоимость

**Модель стоимости.** Единичная стоимость: чтение/запись поля, арифметика,
инкремент/декремент счётчика ссылок. `malloc`/`free` — O(1) (стандартное
допущение; системный аллокатор его формально не гарантирует, это общее
допущение для обеих реализаций). Клонирование значения `T` стоит `c_T` и делает
`a_T` аллокаций (для `i32`: 0 и 0; для `String`: O(длины) и 1).

**Теорема 2.** Каждая операция `push`/`pop` выполняется за
`O(1 + s · c_T)` в худшем случае и делает не более `1 + 2s` (push) или `2s`
(pop) аллокаций узлов и не более `2s` клонирований значений.

*Доказательство.* Копия версии — O(1) (≤ 6 инкрементов в C/Rust). Примитивная
часть — O(1) и не более одного узла (`push`). Старт — O(1). Шаг `σ` создаёт не
более 2 узлов (`Rev`) или 1 (`App`) и клонирует не более 2 значений (при снятии
вершины разделяемого узла). Инвалидация и завершение — O(1) присваиваний.

Освобождения внутри операции — O(1) каждое, без каскада. Во время операции
родитель жив (его держит вызывающий). Все стеки копии на каждом шаге указывают
либо на узлы, достижимые из родителя, либо на узлы, созданные в этой же
операции. Из стеков снимаются только «старые» узлы: из `F`, `F'`, `R'` — всегда
узлы родителя; из `RF` в фазе `App` — узлы, созданные в предыдущих операциях
(в шаге, завершающем `Rev`, `F'` уже пуст, и в `RF` ничего не добавляется).
Узлы, созданные в этой операции, только добавляются на вершины `A`, `RF`, `R` и
не освобождаются до конца операции. Декремент счётчика узла, достижимого из
родителя, не обнуляет его (ссылка от родителя остаётся), значит, освобождения
по цепочке внутри операции не происходит. ∎

При `s = 1`: `push` — не более 3 узлов, `pop` — не более 2 (при `s = 2` — 5 и 4,
что совпадает с измерениями `rust/tests/alloc.rs`).

**Уничтожение версии** (`fqueue_destroy` / `drop`) **не** O(1) в худшем случае ни
при каком `s`. Освобождается каскадом всё, чем версия владела монопольно; это
может быть Θ(n) узлов (например, старый фронт после завершения ротации, когда
удалена последняя ссылающаяся на него версия). Амортизированно это O(1) на
созданный узел: каждый узел создаётся один раз в операции, которая оплачивает
O(1), и освобождается не более одного раза.

**Контракт** (одинаково для C и Rust, при любом `s ≥ 1`):

- Worst-case O(1) (с множителем `c_T` на клонирование значения для
  обобщённого `T: Clone`) гарантируется для **построения новой версии**
  (`push`/`pop`) и **доступа** (`front`, `len`/`size`, `is_empty`).
- **Не** гарантируется для уничтожения версии (`fqueue_destroy`, `Drop`) и,
  следовательно, для произвольного выражения, неявно уничтожающего версию.
  В Rust `q = q.push(x)` складывается из `push(&self)` за O(1) и удаления
  старого значения `q` при присваивании — а это может стоить Θ(n).
  Аналог в C — `fqueue_push(&q2, &q, x); fqueue_destroy(&q);`.
- Уничтожение стоит O(число узлов, которыми версия владела монопольно), в
  сумме по всем версиям — не больше числа созданных узлов, то есть
  амортизированно O(1) на операцию.

## 7. Ограничения и допущения

1. Счётчики ссылок и длины не переполняются (`u32` в обеих реализациях). В
   Rust переполнение счётчика — `abort`, длины — паника; в C операция,
   которая переполнила бы счётчик или длину, не выполняется и возвращает
   `FQUEUE_OVERFLOW`.
2. `malloc`/`free` — O(1) (см. п. 6).
3. Однопоточное использование (счётчики неатомарные в обеих реализациях).
4. Длины (`size`, `front_len`, `rear_len`, `ok`) не переполняются: C — `int`,
   Rust — `usize`.

## 8. Замечание о прежнем обосновании двух шагов

В `docs/c-implementation-notes.md` сказано, что при одном шаге ротация «не успевает» и
`pop` разыменовывает `NULL`. Для текущего кода это неверно. Подсчёт там
предполагает полные `2f + 1` шагов на ротацию, но не учитывает, что каждый `pop`
во время ротации уменьшает и работу фазы `App` (через `ok`). По лемме 3 каждый
`pop` сокращает оставшуюся работу на шаг. Ровно поэтому неравенство из (д) и
п. 2 инварианта выполняются уже при `s = 1`. Для варианта Окасаки, где
завершение и установка фронта — отдельные шаги автомата (`Done`, холостой шаг
при `ok = 0`), это рассуждение неприменимо: там нужны два шага.
