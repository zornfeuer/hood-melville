# Пул узлов (#10)

Альтернативное хранение узлов: узлы берутся из специализированного пула, а
не у системного аллокатора по одному. Пуловые варианты очереди существуют
**рядом** с вариантами на `malloc` — как обычный и потокобезопасный —
и предназначены для пользователей библиотеки как полноценная альтернатива
со своими компромиссами (раздел «Компромиссы»). Варианты по умолчанию не
меняются.

Документ — спецификация: реализации на C, Rust и Zig следуют одному
алгоритму; константы и приёмы, которые в языке ускоряют, а в другом нет,
выбираются по замерам в своём языке (`docs/plan.md`, «Правила для
оптимизаций») и записываются здесь. Отступления в коде без правки этого
файла запрещены.

Версия 2 (#16): узел возвращается владельцу своей плиты. Первая версия
(#10) оставляла узел у освободившего потока и переливала излишки в общий
стек — разбор её констант и замеры v2 против неё ниже.

## Модель

- Один пул на **тип узла** в процессе: все версии этого типа берут и
  возвращают узлы в один пул. Пул статический: создаётся при первом
  выделении, живёт до конца процесса, поэтому переживает любую версию.
- Версия очереди пул не хранит: её размер и раскладка те же, что у варианта
  на `malloc` (Rust и Zig — 64 байта, C — 80).
- Семантика очереди, счётчики ссылок и освобождение узла при обнулении
  счётчика — те же; меняется только то, куда узел уходит: в пул, а не в
  `free`.
- Тип узла:
  - C — одно инстанцирование шаблона (`fqueue_pooled` и `fqueue_pooled_sync`
    — два разных пула);
  - Zig — один тип очереди из `QueueWithOptions`;
  - Rust — одна раскладка узла (размер и выравнивание): обобщённых
    статических переменных в Rust нет, поэтому пулы — по классам размера,
    и очереди с одинаковой раскладкой узла (например, `PooledQueue<i32>` и
    `SyncPooledQueue<u32>`) делят пул. На поведение это не влияет: пул
    потокобезопасен для любых очередей.

## Алгоритм

Константы (одинаковы в трёх языках, выбраны по замерам в каждом):

| имя | значение | смысл |
|---|---:|---|
| `SLAB_BYTES` | 16384 | размер плиты, она же выравнивание |
| `REMOTE_BATCH` | 64 | чужих узлов в пачке, которую поток отдаёт владельцу одной операцией |

Узел пула — память под узел очереди; пока узел свободен, его первое слово
занято пулом (следующий узел списка, пачки или стека освобождений). Размер
узла не меньше двух указателей (у всех трёх реализаций — 16 байт и больше):
столько же занимает заголовок плиты.

**Плиты.** Плита — `SLAB_BYTES`, выровненная по своему размеру, из
стандартного пути выделения языка: C — `FQUEUE_ALIGNED_MALLOC` (по
умолчанию `aligned_alloc`, освобождается `FQUEUE_FREE`), Rust — глобальный
аллокатор с `Layout(16384, 16384)`, Zig — `alignedAlloc` у `allocator`,
переданного в операцию (см. API). Первые байты плиты, округлённые до
размера узла, — заголовок: слово 0 — следующая плита (список всех плит
пула), слово 1 — кэш-владелец; остальное нарезается на узлы. Плита узла —
его адрес, округлённый вниз до `SLAB_BYTES`, поэтому владелец находится по
адресу без поиска.

Размер плиты — страница Apple M (16 КиБ): заголовок лежит на странице
освобождаемого узла, и проверка владельца не тратит лишнюю запись TLB. С
плитами по 64 КиБ проверка стоила 8–16% на `mixed 10^7` (замеры ниже).

**Кэш потока.** У каждого потока на каждый пул: список свободных узлов
(односвязный, LIFO) со счётчиком длины, текущая плита с указателем
нарезки, пачка чужих узлов (владелец, голова, хвост, длина) и стек
освобождений — узлы плит этого кэша, освобождённые другими потоками. Кэш
владеет плитами, которые нарезал. Кэш лежит в куче, а thread-local память
хранит только указатель на него — одинаково в C, Rust и Zig. Причины: в C
деструктор выхода потока — ключ `pthread_key`, а порядок, в котором macOS
освобождает `_Thread_local` и вызывает деструкторы ключей, не определён; в
Rust поля кэша читают и пишут и другие потоки (стек освобождений, `stats`,
`trim`), и ссылка на кэш внутри `thread_local!` была бы гонкой по модели
памяти — все обращения идут через сырой указатель по отдельным полям
(проверено Miri); и на кэш указывают заголовки плит, так что он переживает
поток. Цена — одна зависимая загрузка на операцию, у всех трёх одинаковая.

В Rust `thread_local!` с указателями — без деструктора: доступ к
thread-local с деструктором проверяет его состояние на каждой операции
(с ним Rust-пул был на 10% медленнее на `fill`); выход потока обслуживает
отдельный thread-local-охранник, которого трогает только регистрация кэша.

Кэш потока занимает свою строку кэша (выравнивание 128 байт): кэши разных
потоков меняются на каждой операции. Стек освобождений — в отдельной строке:
его пишут другие потоки.

**Выделение** (по порядку):
1. из списка свободных потока;
2. стек освобождений целиком (`exchange` на null) — в начало списка;
3. нарезка из текущей плиты потока;
4. новая плита (под блокировкой пула — только вставка в список плит).

**Порядок переиспользования — LIFO** (последний освобождённый узел выдаётся
первым; обоснование — «Предварительная диагностика» ниже). Порядок узлов,
забранных из стека освобождений, на скорость не влияет (проверено: прямой,
обратный и по пачкам — в пределах шума).

**Освобождение.** Владелец плиты узла — текущий кэш: узел в список свободных
потока. Иначе узел в пачку потока для его владельца; если в пачке узлы
другого владельца, она сначала уходит своему; полная пачка (`REMOTE_BATCH`)
уходит сразу. Пачка уходит в стек освобождений владельца одной операцией
(CAS с release; владелец забирает с acquire). Стек только пополняется
другими потоками и забирается целиком, поэтому ABA нет. Поток без кэша
(не удалось выделить или поток завершается) отдаёт узел владельцу сразу.

Без пачек каждый освобождённый чужой узел — CAS на одном указателе, за
который борются все освобождающие потоки: в snapshot читатели были на 35%
медленнее.

**Резерв операций на месте** (C, Zig — там, где есть гарантия «при ошибке
без изменений»): узлы шага ротации не выделяются заранее, а резервируются —
в кэше потока (список, затем ненарезанный остаток плиты) должно быть не
меньше нужного числа, иначе сейчас же забирается стек освобождений или
берётся новая плита (только это может отказать, до изменения очереди).
Узлы выделяет сам шаг — после своих освобождений: выделение заранее меняло
бы их порядок, а при LIFO-переиспользовании порядок задаёт раскладку
(`mixed_mut 10^7` −25–27%, `docs/benchmarks.md`, «Цена гарантии на пуле…»).
Ненарезанный остаток прежней плиты при этом остаётся до `trim`.

**Выход потока:** пачка чужих узлов уходит владельцу, кэш со всем остальным
(список, стек освобождений, плиты и остаток текущей) становится сиротой —
его возьмёт следующий поток, которому нужен кэш. C — деструктор
`pthread_key`; Rust — `Drop` у thread-local-охранника; Zig — деструкторов у
`threadlocal` нет, поэтому явный `flushThreadCache()`; без него кэш
завершившегося потока удерживается до `trim`. Кэши не освобождаются, пока
есть плиты (на них указывают заголовки): C и Rust держат кэши до конца
процесса, Zig освобождает кэши сирот в `trim` (иначе пул не пуст целиком и
аллокатор нельзя сменить).

**Реестр кэшей.** Кэш потока регистрируется в пуле при создании и остаётся
в реестре навсегда (сироты тоже) — для `stats` и `trim`. Блокировка пула —
спин-блокировка test-and-test-and-set, при занятости — уступка процессора;
под ней только список плит, реестр и сироты (в Zig 0.16 мьютексу нужен
`Io`, а критическая секция — пара указателей).

**Поток без кэша в Rust.** Выделение из деструктора другого thread-local
значения после выхода охранника: общий кэш класса под своей блокировкой
(в C после деструктора ключа поток продолжает работать с осиротевшим кэшем,
как и v1 — с освобождённым: пул нельзя использовать из деструкторов
`pthread_key` после деструктора пула; Zig — после `flushThreadCache`
поток просто заводит кэш заново).

**Отличия по языкам.**
- C и Zig: освобождение в потокобезопасных вариантах — вызовом
  (`fqueue_impl_npool_free_outlined`, `freeOutlined`), в остальных
  встраивается. Встроенное, оно меняло встраивание путей освобождения: C
  +54 млн инструкций на `mixed_mut 10^6` (sync +2.5–4.5% на `mixed` против
  v1), Zig sync `mixed` +14%, `mixed_mut` +19%; вызовом — C вровень с v1,
  Zig +4% и +10%. В обычных вариантах встроенное быстрее (C `mixed_mut
  10^6` 0.91 против 0.94, Zig 1.00 против 1.04).
- Rust: аллокатор не знает, атомарные ли счётчики у очереди (`deallocate`
  получает только раскладку), поэтому выбрать по варианту нельзя;
  освобождение встраивается (sync `mixed` +2–3% против v1).
- Zig: кэш — `extern struct`: обычную структуру Zig переупорядочивает, и
  `nfree` уходил в строку стека освобождений (освобождение трогало две
  строки: `mixed_mut 10^6` +7%, sync +30%). В C и Rust порядок полей —
  как написан (C) или сводит поля кэша в одну строку (Rust: поле с
  выравниванием 128 — отдельно).

  `mixed 10^7` окажется важен; v1 — LIFO.

## v1: константы перелива (история)

В v1 освобождённый узел оставался у освободившего потока, список длиннее
`CACHE_MAX` отдавал `BATCH` узлов в общий стек пачек под спин-блокировкой,
пустой — забирал пачку оттуда. Первый вариант (`CACHE_MAX` 512, `BATCH` 256) в параллельной нагрузке
(`fqueue_par`, у каждой задачи своя очередь) не масштабировалась совсем: C,
share 0, P=10 — 110–155 мс против 38–46 у системного `malloc`, при P=1 пул
быстрее; IPC 0.9 против 5. Причина — перелив: пачка уходит в общий стек,
её забирает другой поток, а соседние узлы тех же 128-байтовых строк (8 узлов
по 16 байт) остаются у прежнего; два потока пишут в одни строки (ложное
разделение). Без предела кэша пул масштабируется (34 мс), но в схеме
«выделяет один поток, освобождают другие» (snapshot) память растёт без
ограничения (пик 20–32 МиБ против 2). Перебор (C, `fqueue_par`, мс; 3
прогона):

| `CACHE_MAX` / `BATCH` | share 0, P=10 | share 1%, P=10 | snapshot R=4 | snapshot R=9 | пик R=9 |
|---|---:|---:|---:|---:|---:|
| 512 / 256 | 110–155 | 192–194 | 188–223 | 291–297 | 2.2 МиБ |
| 2048 / 1024 | 29–45 | 87–90 | 198–231 | 263–283 | 2.2 МиБ |
| 4096 / 2048 | 29–41 | 87–89 | 187–197 | 254–267 | 2.4 МиБ |
| 8192 / 4096 | 29–46 | 88 | 178–191 | 247–260 | 2.7 МиБ |
| системный `malloc` | 38–46 | 83–90 | 120–151 | 162–209 | 2.2 МиБ |

Принято 4096 / 2048 — кэш в плиту узлов: переливы редки, память
ограничена. Выравнивание кэша на строку проверено отдельно и само по себе
не помогало (ложное разделение — по узлам, не по кэшам), но оставлено.

Слабое место, которое константами не убрать, — snapshot: писатель
выделяет, читатели освобождают, узлы ходят по кругу через общий стек, и
строки снова оказываются у разных потоков (писатель в 1.3–1.5 раза
медленнее, чем с системным `malloc`). Убрать его может только возврат узла
владельцу его плиты (как в mimalloc: плиты, выровненные по размеру, и
список освобождений от чужих потоков у владельца) — это v2.

  освобождении (C — до 13%).
- В snapshot читатели быстрее v1 на 19–43% у всех трёх; писатель — от −17%
  до +25%: писатель и читатели делят одни счётчики и мьютекс, и медленные
  читатели разгружают писателя (обе колонки надо читать вместе).
- Разрыв snapshot с системным `malloc` v2 сокращает, но не закрывает: пул
  отстаёт и при R=1, где конкуренции почти нет. Пачки и порядок выдачи
  узлов на это не влияют; по ранним опытам (`docs/benchmarks.md`, «Разница
  C и Rust в snapshot») решает раскладка узлов при LIFO-переиспользовании —
  отдельная задача.

Опыты прототипа на C (решения выше):
- плиты 64 КиБ — проверка владельца стоила 8–16% на `mixed 10^7`
  (сборка без проверки: −8…−11%); 16 КиБ (страница) — большая часть ушла,
  256 КиБ — хуже; это TLB: заголовок на другой странице;
- без пачек чужих освобождений читатели в snapshot на 35% медленнее (CAS
  на каждый узел в один стек); пачки 16, 64 и 256 — одинаково, взята 64;
- порядок узлов, забранных из стека освобождений (как есть, обратный,
  пачки по порядку освобождения), на snapshot не влияет;
- загрузка заголовка следующего узла заранее, вместе с его счётчиком, —
  хуже на 1–3%;
- освобождение вызовом в sync-вариантах — см. «Отличия по языкам».

## Память

Политика:
- плиты автоматически системе **не возвращаются**: удерживаемая пулом
  память равна пику живого множества (с точностью до кэшей потоков); в v2 —
  по каждому потоку-владельцу: свободные узлы живого потока другим потокам
  не достаются (в v1 излишки переливались в общий стек), их получит только
  тот, кто подберёт кэш после выхода потока;
- `trim()` возвращает все плиты, если живых узлов нет, и иначе ничего не
  делает; возвращает число освобождённых байт. Вызывать в спокойном
  состоянии: ни один другой поток в это время не пользуется пулом (кэши
  других потоков сбрасываются из вызывающего);
- возврат отдельных плит (счётчик живых узлов на плиту) — только если
  замеры удержания (сценарий `wave`, #14) покажут, что он нужен; в
  потокобезопасном варианте это ещё одна атомарная операция на каждое
  выделение и освобождение.

**Статистика** (`stats`): число плит и байт плит, ёмкость в узлах, свободные
узлы (списки кэшей, пачки, стеки освобождений, ненарезанные остатки), живые
= ёмкость − свободные, обращения к системе (выделения и освобождения плит),
сколько раз владельцы забрали стек освобождений (`collects`) и сколько
кэшей сирот подобрали новые потоки (`adoptions`). Стек освобождений
считается так: забрать целиком, посчитать, вернуть. Под конкуренцией —
приблизительная. В v1 вместо двух последних счётчиков были переливы и
пачки (`spills`, `refills`).

## API

**C** — опция инстанцирования рядом с `FQUEUE_ATOMIC`:
```c
#define FQUEUE_NAME pq
#define FQUEUE_T    int
#define FQUEUE_NODE_POOL
#include "fqueue_template.h"
// API очереди без изменений: pq_init, pq_push, pq_push_in_place, ...
void   pq_pool_stats(fqueue_pool_stats *out);
size_t pq_pool_trim(void);
```
Готовые `fqueue_pooled` и `fqueue_pooled_sync` объявлены в `fqueue.h`.
Гарантия «при ошибке очередь не меняется» прежняя: отказать может только
получение плиты (`FQUEUE_NOMEM`). Плиты выровнены, поэтому с
`FQUEUE_MALLOC`/`FQUEUE_FREE` пулу нужен и `FQUEUE_ALIGNED_MALLOC(alignment,
size)` (блок, который освобождает `FQUEUE_FREE`, как `aligned_alloc` и
`free`); без него инстанцирование с пулом не компилируется.

**Rust** — аллокатор `NodePool` в параметре очереди `A: Allocator` (как
`Vec<T, A>`; Rust 1.100, #20):
```rust
pub type PooledQueue<T> = Queue<T, Local, NodePool>;
pub type SyncPooledQueue<T> = SyncQueue<T, NodePool>; // Queue<T, Atomic, NodePool>
let q = PooledQueue::new_pooled().push(1); // = Queue::new_in(NodePool)
hood_melville::pool::stats();   // сумма по всем пулам
hood_melville::pool::trim();
```
`NodePool` без размера (пул один на процесс), поэтому версия та же — 64
байта. Класс размера считается из `Layout` и после встраивания — константа;
блоки больше 256 байт, с выравниванием больше 16 и нулевого размера пул
передаёт `Global`, так что `NodePool` годится и для `Box`/`Vec`. До #20 —
фича `pool` и политика `Pooled<R>` во втором параметре: функции узла
дублировались под `cfg`, чтобы код без пула оставался побайтно прежним; с
параметром аллокатора код один (`docs/benchmarks.md`, #20).

**Zig** — опция в `QueueWithOptions` и готовые типы:
```zig
const Q = hm.PooledQueue(i32); // QueueWithOptions(i32, .{ .nodes = .pool })
// hm.SyncPooledQueue(i32) — с атомарными счётчиками
var q2 = try q.push(allocator, 42); // allocator — источник плит
const s = Q.node_pool.stats();       // hm.PoolStats
_ = Q.node_pool.trim(allocator);
Q.node_pool.flushThreadCache();      // перед выходом потока
```
Операции сохраняют параметр `allocator`, но для пулового типа это
источник плит (выровненных, `alignedAlloc`) и кэшей потоков, а не узлов: пул запоминает его при первой
плите и в Debug и ReleaseSafe проверяет, что передаётся тот же (на горячем
пути параметр не используется). Сменить источник можно, когда пул пуст
целиком: кэши всех потоков сброшены (`flushThreadCache`) и плиты возвращены
(`trim`). Так API пулового типа совпадает с обычным — обобщённый код не
меняется, — и источник памяти, как принято в Zig, виден в месте вызова.
Пространство имён — `node_pool`, а не `pool`: в Zig нельзя затенять имена, а
`pool` уже занято резервом узлов операций на месте. Код очереди без пула
тот же (сверено по машинному коду `fqueue_bench`: отличаются только имена
типов).

## Ограничения

- Память удерживается до `trim` (пик живого множества; свободные узлы
  живого потока другим потокам не достаются).
- Поток, освобождающий чужие узлы, держит до `REMOTE_BATCH` из них в своей
  пачке, пока не освободит узел другого владельца, не наберёт пачку или не
  завершится (в `stats` они свободные).
- `trim` — только в спокойном состоянии.
- Zig: кэш потока перед выходом сбрасывать явно
  (`node_pool.flushThreadCache`).
- C: пулом нельзя пользоваться из деструкторов `pthread_key` того же потока
  после деструктора пула (кэш уже отдан сиротам).
- В Zig все операции одного пулового типа должны получать один и тот же
  `allocator` (сменить — только когда пул пуст целиком).
- Тесты пула не идут через `checkAllAllocationFailures` (Zig): каждый
  прогон подставляет новый аллокатор, а пулу нужен один источник плит; отказ
  выделения плиты и кэша проверен отдельным тестом.
- `fork` при живых кэшах других потоков не поддерживается.
- Отладка памяти: AddressSanitizer не видит обращения к узлу после его
  возврата в пул (память плит не освобождается до `trim`); ошибки
  владения ловит вариант на `malloc` — тесты гоняются на обоих.
- ThreadSanitizer не моделирует барьеры памяти: при переиспользовании узла
  другим потоком он сообщил бы о гонке между release-декрементом счётчика
  и записью пула в узел. Поэтому под TSan последний владелец делает
  acquire-загрузку счётчика вместо acquire-барьера (как `Arc` в Rust под
  TSan); в обычных сборках — барьер.

## Компромиссы

| | `malloc` (по умолчанию) | пул |
|---|---|---|
| цена выделения | вызов аллокатора | несколько инструкций из списка потока |
| возврат памяти | по узлу, как решит аллокатор | только `trim` при нуле живых |
| удержание | зависит от аллокатора | пик живого множества по потокам-владельцам |
| чужой поток освобождает | как решит аллокатор | узел возвращается владельцу пачкой |
| владение | нет общего состояния | глобальный пул на тип, кэши потоков |
| зависимость от аллокатора | полная (режимы, #8) | только источник плит |

## Честность сравнения

- Один алгоритм (этот документ); константы и приёмы выбираются по замерам
  в каждом языке и записываются здесь (`docs/plan.md`, «Правила для
  оптимизаций»); сверка по статистике пула: число плит у трёх языков
  совпадает на одной однопоточной нагрузке.
- Раскладка версии та же, что у варианта на `malloc`: A/B «пул против
  `malloc`» внутри языка меряет только пул.
- Тот же исходник бенчмарка, вариант выбирается на этапе компиляции;
  контрольные суммы совпадают.
- 4 раскладки кода, запуски вперемешку; пул — ещё одно «хранение узлов» в
  сетках #8 рядом с системным `malloc`, mimalloc и jemalloc.
- Горячий путь в Zig — без вызова через vtable `Allocator` (в C и Rust он
  встраивается).
- Форма горячих путей сверяется по машинному коду. В Rust v1 это потребовало двух правок,
  найденных по машинному коду: освобождение цепочки узлов — отдельной
  функцией после проверки счётчика (с #20 — для любого аллокатора) (как `release` в C; иначе адрес кэша и
  сохранение регистров платило каждое отпускание ссылки), и `thread_local!`
  без деструктора (см. «Кэш потока»). Вместе — `fill 10^6` 176 → 128 млн
  тактов, на уровне C (120), `persistent` 502 → 390 (C 390).
