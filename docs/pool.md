# Пул узлов (#10)

Альтернативное хранение узлов: узлы берутся из специализированного пула, а
не у системного аллокатора по одному. Пуловые варианты очереди существуют
**рядом** с вариантами на `malloc` — как обычный и потокобезопасный —
и предназначены для пользователей библиотеки как полноценная альтернатива
со своими компромиссами (раздел «Компромиссы»). Варианты по умолчанию не
меняются.

Документ — спецификация: реализации на C, Rust и Zig обязаны следовать
одному алгоритму с одними константами, иначе сравнение в бенчмарках
нечестно. Отступления от спецификации в коде запрещены без правки этого
файла.

## Модель

- Один пул на **тип узла** в процессе: все версии этого типа берут и
  возвращают узлы в один пул. Пул статический: создаётся при первом
  выделении, живёт до конца процесса, поэтому переживает любую версию.
- Версия очереди пул не хранит: её размер и раскладка те же, что у варианта
  на `malloc` (Rust и Zig — 64 байта, C — 80).
- Семантика очереди, счётчики ссылок и освобождение узла при обнулении
  счётчика — те же; меняется только то, куда узел уходит: в пул, а не в
  `free`.
- Тип узла:
  - C — одно инстанцирование шаблона (`fqueue_pooled` и `fqueue_pooled_sync`
    — два разных пула);
  - Zig — один тип очереди из `QueueWithOptions`;
  - Rust — одна раскладка узла (размер и выравнивание): обобщённых
    статических переменных в Rust нет, поэтому пулы — по классам размера,
    и очереди с одинаковой раскладкой узла (например, `PooledQueue<i32>` и
    `SyncPooledQueue<u32>`) делят пул. На поведение это не влияет: пул
    потокобезопасен для любых очередей.

## Алгоритм

Константы:

| имя | значение | смысл |
|---|---:|---|
| `SLAB_BYTES` | 65536 | размер плиты |
| `CACHE_MAX` | 4096 | предел списка свободных у потока, узлов (плита 16-байтовых) |
| `BATCH` | 2048 | узлов в пачке при переливе в общий список и обратно |

Узел пула — память под узел очереди; пока узел свободен, его первые два
слова заняты пулом (следующий узел в списке, следующая пачка). Размер узла
не меньше двух указателей (у всех трёх реализаций — 16 байт и больше).

**Плиты.** Плита — `SLAB_BYTES` из стандартного пути выделения языка: C —
`FQUEUE_MALLOC` (по умолчанию `malloc`), Rust — глобальный аллокатор
(`std::alloc::alloc`), Zig — `allocator`, переданный в операцию (см. API).
Первые байты плиты, округлённые до размера узла, — заголовок (указатель на
следующую плиту — список всех плит пула); остальное нарезается на узлы.

**Кэш потока.** У каждого потока на каждый пул: список свободных узлов
(односвязный, LIFO) со счётчиком длины и текущая плита с указателем
нарезки. Кэш лежит в куче, а thread-local память хранит только указатель на
него — одинаково в C, Rust и Zig. Причины: в C деструктор выхода потока —
ключ `pthread_key`, а порядок, в котором macOS освобождает `_Thread_local`
и вызывает деструкторы ключей, не определён; в Rust поля кэша меняют и
другие потоки (реестр, `trim`), и ссылка на кэш внутри `thread_local!`
(включая `&mut` его деструктора) была бы гонкой по модели памяти — все
обращения идут через сырой указатель по отдельным полям (проверено Miri).
Цена — одна зависимая загрузка на операцию, у всех трёх одинаковая.

В Rust `thread_local!` с указателями — без деструктора: доступ к
thread-local с деструктором проверяет его состояние на каждой операции
(с ним Rust-пул был на 10% медленнее на `fill`); выход потока обслуживает
отдельный thread-local-охранник, которого трогает только регистрация кэша.

**Выделение** (по порядку):
1. из списка свободных потока;
2. пачка из общего списка (целиком в список потока);
3. нарезка из текущей плиты потока;
4. новая плита (под блокировкой пула — только вставка в список плит).

**Порядок переиспользования — LIFO** (последний освобождённый узел выдаётся
первым; обоснование — «Предварительная диагностика» ниже).

Кэш потока занимает свою строку кэша (выравнивание 128 байт): кэши разных
потоков меняются на каждой операции.

**Резерв операций на месте** (C, Zig — там, где есть гарантия «при ошибке
без изменений»): узлы шага ротации не выделяются заранее, а резервируются —
в кэше потока (список, затем ненарезанный остаток плиты) должно быть не
меньше нужного числа, иначе сейчас же берётся пачка или новая плита (только
это может отказать, до изменения очереди). Узлы выделяет сам шаг — после
своих освобождений: выделение заранее меняло бы их порядок, а при
LIFO-переиспользовании порядок задаёт раскладку (`mixed_mut 10^7` −25–27%,
`docs/benchmarks.md`, «Цена гарантии на пуле…»).

**Освобождение:** в список свободных потока, который освобождает (узел,
выделенный другим потоком, остаётся у освободившего). Если длина списка
превысила `CACHE_MAX`, `BATCH` узлов с вершины уходят одной пачкой в общий
список.

**Общий список** — стек пачек под спин-блокировкой
(test-and-test-and-set, при занятости — уступка процессора). Одинакова во
всех трёх языках; системный мьютекс не используется: в Zig 0.16 мьютексу
нужен `Io`, а критическая секция — пара указателей, и заходят в неё раз на
сотни операций.

**Выход потока:** список свободных потока пачками уходит в общий список,
остаток текущей плиты остаётся неиспользованным до `trim` (не теряется для
учёта). C — деструктор `pthread_key`; Rust — `Drop` у `thread_local!`;
Zig — деструкторов у `threadlocal` нет, поэтому явный
`flushThreadCache()`; без него кэш завершившегося потока (до `CACHE_MAX`
узлов и остаток плиты) удерживается до `trim`.

**Реестр кэшей.** Кэш потока регистрируется в пуле при первом
использовании и снимается при выходе потока — для `stats` и `trim`.

  `mixed 10^7` окажется важен; v1 — LIFO.

## Многопоточность: почему такие константы

Первая версия (`CACHE_MAX` 512, `BATCH` 256) в параллельной нагрузке
(`fqueue_par`, у каждой задачи своя очередь) не масштабировалась совсем: C,
share 0, P=10 — 110–155 мс против 38–46 у системного `malloc`, при P=1 пул
быстрее; IPC 0.9 против 5. Причина — перелив: пачка уходит в общий стек,
её забирает другой поток, а соседние узлы тех же 128-байтовых строк (8 узлов
по 16 байт) остаются у прежнего; два потока пишут в одни строки (ложное
разделение). Без предела кэша пул масштабируется (34 мс), но в схеме
«выделяет один поток, освобождают другие» (snapshot) память растёт без
ограничения (пик 20–32 МиБ против 2). Перебор (C, `fqueue_par`, мс; 3
прогона):

| `CACHE_MAX` / `BATCH` | share 0, P=10 | share 1%, P=10 | snapshot R=4 | snapshot R=9 | пик R=9 |
|---|---:|---:|---:|---:|---:|
| 512 / 256 | 110–155 | 192–194 | 188–223 | 291–297 | 2.2 МиБ |
| 2048 / 1024 | 29–45 | 87–90 | 198–231 | 263–283 | 2.2 МиБ |
| 4096 / 2048 | 29–41 | 87–89 | 187–197 | 254–267 | 2.4 МиБ |
| 8192 / 4096 | 29–46 | 88 | 178–191 | 247–260 | 2.7 МиБ |
| системный `malloc` | 38–46 | 83–90 | 120–151 | 162–209 | 2.2 МиБ |

Принято 4096 / 2048 — кэш в плиту узлов: переливы редки, память
ограничена. Выравнивание кэша на строку проверено отдельно и само по себе
не помогало (ложное разделение — по узлам, не по кэшам), но оставлено.

Слабое место, которое константами не убрать, — snapshot: писатель
выделяет, читатели освобождают, узлы ходят по кругу через общий стек, и
строки снова оказываются у разных потоков (писатель в 1.3–1.5 раза
медленнее, чем с системным `malloc`). Убрать его может только возврат узла
владельцу его плиты (как в mimalloc: плиты, выровненные по размеру, и
список освобождений от чужих потоков у владельца) — кандидат для v2.

## Память

Политика v1:
- плиты автоматически системе **не возвращаются**: удерживаемая пулом
  память равна пику живого множества (с точностью до кэшей потоков);
- `trim()` возвращает все плиты, если живых узлов нет, и иначе ничего не
  делает; возвращает число освобождённых байт. Вызывать в спокойном
  состоянии: ни один другой поток в это время не пользуется пулом (кэши
  других потоков сбрасываются из вызывающего);
- возврат отдельных плит (счётчик живых узлов на плиту) — v2, только если
  замеры удержания (сценарий `wave`, #14) покажут, что он нужен; в
  потокобезопасном варианте это ещё одна атомарная операция на каждое
  выделение и освобождение.

**Статистика** (`stats`): число плит и байт плит, ёмкость в узлах, свободные
узлы (кэши, общий список, ненарезанные остатки), живые = ёмкость −
свободные, обращения к системе (выделения и освобождения плит), переливы в
общий список и пачки из него. Под конкуренцией — приблизительная.

## API

**C** — опция инстанцирования рядом с `FQUEUE_ATOMIC`:
```c
#define FQUEUE_NAME pq
#define FQUEUE_T    int
#define FQUEUE_NODE_POOL
#include "fqueue_template.h"
// API очереди без изменений: pq_init, pq_push, pq_push_in_place, ...
void   pq_pool_stats(fqueue_pool_stats *out);
size_t pq_pool_trim(void);
```
Готовые `fqueue_pooled` и `fqueue_pooled_sync` объявлены в `fqueue.h`.
Гарантия «при ошибке очередь не меняется» прежняя: отказать может только
получение плиты (`FQUEUE_NOMEM`).

**Rust** — фича `pool` и политика узлов `Pooled<R>` в существующем
параметре очереди (счётчик `R` — `Local` или `Atomic`, узлы — из пула):
```rust
// Cargo.toml: hood-melville = { version = "…", features = ["pool"] }
pub type PooledQueue<T> = Queue<T, Pooled<Local>>;
pub type SyncPooledQueue<T> = Queue<T, Pooled<Atomic>>;
let q = PooledQueue::new_pooled().push(1);
hood_melville::pool::stats();   // сумма по всем пулам
hood_melville::pool::trim();
```
Не третий параметр типа (`Queue<T, R, S>`), как задумывалось сначала: «как
живёт узел» — одна ось (счётчик и хранение), версия та же (64 байта), а
меняется только `node.rs` вместо всех обобщённых типов. Без фичи код пула не
компилируется: даже мелкая перестройка MIR в `node.rs` меняла решения LLVM о
встраивании в нагрузке, поэтому функции, создающие и забирающие узел, — в двух
вариантах под `cfg`, и сборка без фичи побайтно прежняя (сверено по
машинному коду `fqueue_bench`). Узлы больше 256 байт пулом не
поддерживаются (ошибка компиляции): храните `Box<T>`.

**Zig** — опция в `QueueWithOptions` и готовые типы:
```zig
const Q = hm.PooledQueue(i32); // QueueWithOptions(i32, .{ .nodes = .pool })
// hm.SyncPooledQueue(i32) — с атомарными счётчиками
var q2 = try q.push(allocator, 42); // allocator — источник плит
const s = Q.node_pool.stats();       // hm.PoolStats
_ = Q.node_pool.trim(allocator);
Q.node_pool.flushThreadCache();      // перед выходом потока
```
Операции сохраняют параметр `allocator`, но для пулового типа это
источник плит (и кэшей потоков), а не узлов: пул запоминает его при первой
плите и в Debug и ReleaseSafe проверяет, что передаётся тот же (на горячем
пути параметр не используется). Сменить источник можно, когда пул пуст
целиком: кэши всех потоков сброшены (`flushThreadCache`) и плиты возвращены
(`trim`). Так API пулового типа совпадает с обычным — обобщённый код не
меняется, — и источник памяти, как принято в Zig, виден в месте вызова.
Пространство имён — `node_pool`, а не `pool`: в Zig нельзя затенять имена, а
`pool` уже занято резервом узлов операций на месте. Код очереди без пула
тот же (сверено по машинному коду `fqueue_bench`: отличаются только имена
типов).

## Ограничения

- Память удерживается до `trim` (пик живого множества).
- `trim` — только в спокойном состоянии.
- Zig: кэш потока перед выходом сбрасывать явно
  (`node_pool.flushThreadCache`).
- В Zig все операции одного пулового типа должны получать один и тот же
  `allocator` (сменить — только когда пул пуст целиком).
- Тесты пула не идут через `checkAllAllocationFailures` (Zig): каждый
  прогон подставляет новый аллокатор, а пулу нужен один источник плит; отказ
  выделения плиты и кэша проверен отдельным тестом.
- `fork` при живых кэшах других потоков не поддерживается.
- Отладка памяти: AddressSanitizer не видит обращения к узлу после его
  возврата в пул (память плит не освобождается до `trim`); ошибки
  владения ловит вариант на `malloc` — тесты гоняются на обоих.
- ThreadSanitizer не моделирует барьеры памяти: при переиспользовании узла
  другим потоком он сообщил бы о гонке между release-декрементом счётчика
  и записью пула в узел. Поэтому под TSan последний владелец делает
  acquire-загрузку счётчика вместо acquire-барьера (как `Arc` в Rust под
  TSan); в обычных сборках — барьер.

## Компромиссы

| | `malloc` (по умолчанию) | пул |
|---|---|---|
| цена выделения | вызов аллокатора | несколько инструкций из списка потока |
| возврат памяти | по узлу, как решит аллокатор | только `trim` при нуле живых |
| удержание | зависит от аллокатора | пик живого множества |
| владение | нет общего состояния | глобальный пул на тип, кэши потоков |
| зависимость от аллокатора | полная (режимы, #8) | только источник плит |

## Честность сравнения

- Один алгоритм и константы (этот документ); сверка по статистике пула:
  число плит, переливов и пачек у трёх языков совпадает на одной нагрузке.
- Раскладка версии та же, что у варианта на `malloc`: A/B «пул против
  `malloc`» внутри языка меряет только пул.
- Тот же исходник бенчмарка, вариант выбирается на этапе компиляции;
  контрольные суммы совпадают.
- 4 раскладки кода, запуски вперемешку; пул — ещё одно «хранение узлов» в
  сетках #8 рядом с системным `malloc`, mimalloc и jemalloc.
- Горячий путь в Zig — без вызова через vtable `Allocator` (в C и Rust он
  встраивается).
- Одинаковая форма горячих путей. В Rust это потребовало двух правок,
  найденных по машинному коду: освобождение цепочки узлов — отдельной
  функцией после проверки счётчика (как `release` в C; иначе адрес кэша и
  сохранение регистров платило каждое отпускание ссылки), и `thread_local!`
  без деструктора (см. «Кэш потока»). Вместе — `fill 10^6` 176 → 128 млн
  тактов, на уровне C (120), `persistent` 502 → 390 (C 390).
