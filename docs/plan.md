# План проекта

Состояние на 2026-11-11. Три реализации Hood–Melville (C, Rust, Zig) с
одинаковым алгоритмом, однопоточные и параллельные бенчмарки, журнал
оптимизаций — `docs/benchmarks.md`.

## Что уже можно утверждать

- Однопоточно три реализации близки: Rust / C 1.00–1.12 на персистентных
  операциях, 0.82–0.96 на месте; Zig / C 0.99–1.13 после первого прохода
  оптимизации (#1; было 1.13–1.33 и до 2× на месте). Строки с режимами
  аллокатора (`mixed_mut 10^7`) — не свойство языков.
- Параллельно: масштабирование ломается уже на 1% операций над общими
  версиями, от 5% три реализации совпадают — цена когерентности счётчиков
  ссылок в узлах, следствие устройства структуры, а не языка.
- Разница C и Rust в сценарии snapshot — не в коде языков (работа над общей
  памятью одинакова), но её механизм и связь с системным `malloc` не
  доказаны (`docs/benchmarks.md`, «Разница C и Rust в snapshot»).

Все цифры — с одной машины (Apple M5, macOS 27, системный `malloc`) и одного
набора параметров нагрузки.

## Правила для выводов

- Утверждение «язык X быстрее Y» попадает в README без оговорок, только если
  держится на двух платформах и трёх аллокаторах (системный, mimalloc,
  jemalloc). Остальное — с явной пометкой условий («M5, системный malloc»).
- Аллокатор — фактор эксперимента, как число потоков. Основная база —
  системный `malloc` (то, что получит пользователь); одинаковое размещение
  узлов — только диагностика («одинаков ли код»), не база.
- Публикуются распределения, а не только медианы: где есть режимы
  (бимодальность), указывается доля каждого.
- Доказанное и гипотезы в документах разделяются явно.
- Инструменты измерений проверяются на себе: подставные аллокаторы и
  перехватчики сами могут давать ложное разделение (так было с данными
  потоков в первом варианте аллокатора для snapshot).

## Этапы

Порядок важен: оптимизируем только там, где разрыв устойчив, и сначала
выравниваем условия сравнения.

### 1. Zig: первый проход оптимизации — #1 (сделано)

Итог: все пункты #1 проверены, Zig / C 0.99–1.13; порог ≤ 1.10 не достигнут
на `persistent` (1.13) и `fill_mut 10^6` (1.12) — разбор в журнале
(`docs/benchmarks.md`, «Zig: первый проход оптимизации»). Продолжение — только
если остаток переживёт вторую платформу.

Единственная оптимизация, оправданная сейчас: разрыв Zig с C однопоточный,
большой (до 2× на операциях на месте) и не зависит от аллокатора и
параллельной динамики.

Остановка: Zig / C ≤ 1.10 по медиане на каждом однопоточном сценарии
(персистентные и на месте), **или** все пункты
#1 проверены и записаны в журнал (принято/отклонено с цифрами). Каждое
изменение — A/B по тактам (`bench/compare.py`), тесты и утечки зелёные.
Оговорка: у Zig одна раскладка кода (#4), поэтому вывод «принято» требует
выигрыша больше разброса раскладок, наблюдавшегося у C/Rust (~5%).

### 2. Zig: честный пул в параллельной нагрузке — #7

Не оптимизация, а исправление условий сравнения (`std.Io.Group` занимает
≈ 6.6 ядра из 10). Остановка: Zig pool ≥ Zig threads при share 0, ~9 ядер
по rusage; таблицы в `docs/benchmarks.md` и README обновлены.

### 3. Закрыть вопрос snapshot (ограничено по времени: ~1 день)

Три опыта, после них — запись итога при любом результате:
1. Трасса адресов `malloc`/`free` C и Rust в одном потоке при одинаковом
   LIFO-аллокаторе — первое расхождение последовательностей.
2. Узел, выровненный на строку кэша (128 байт), в C и Rust — вклад ложного
   разделения соседних узлов снимка; с системным `malloc`.
3. `fqueue_par snapshot` с подставными аллокаторами (LIFO, исправленный
   карантин, без переиспользования): повторяется ли картина микротеста в
   самом бенчмарке.

Остановка: три опыта записаны. Если механизм не найден — пишется «не
установлено», дальше в микроархитектуру M5 не идём (это знание о машине, а не
о структуре).

### 4. Аллокаторы — #8

Системный `malloc`, mimalloc, jemalloc одинаково во всех трёх языках;
однопоточная и параллельная нагрузка, включая snapshot. Остановка: таблица по
всем сочетаниям; выводы о языках переформулированы по правилам выше.

### 5. Вторая платформа и сетка параметров

- Linux на x86-64 или Graviton: `just bench-*`, `just bench-par`.
- snapshot: размер снимка, период публикации, размер элемента (`i32` и
  тип побольше) — небольшая сетка.

Остановка: для каждого вывода из README указано, на скольких платформах и
аллокаторах он держится.

### 6. Инфраструктура — #4

PMU по потокам (kperf, перехват `pthread_create`), подставные аллокаторы,
подсчёт операций над счётчиками, зонд инструкций — в `bench/` с описанием;
`just bench-quick`. Раскладки кода для Zig сделаны (`just zig-layout-bc`). Делается по мере надобности для
этапов 1–5, а не отдельно.

### Заморожено

- #2 (остаток разрыва Rust на персистентных операциях) и #3 (операции на
  месте в C, 64 байта) — разрывы малы и зависят от раскладки кода;
  возвращаемся, только если они переживут этап 5.

## Решение о статье

После этапа 5. Кандидат на основной результат — методологический: при
честно одинаковом алгоритме разница языков в персистентной структуре со
счётчиками ссылок меньше, чем эффекты аллокатора, когерентности и раскладки
кода; инструменты (подсчёт операций, PMU по потокам, подставные аллокаторы)
это показывают. Без второй платформы и аккуратной статистики — это заметка
про M5, а не статья.
